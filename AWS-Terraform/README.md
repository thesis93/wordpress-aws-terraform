# Highly-Available WordPress on AWS (Terraform)

This project provisions the architecture from the diagram: a two-AZ VPC with a
public tier (Application Load Balancer + NAT Gateway) and a private tier (an
Auto Scaling fleet of WordPress EC2 instances backed by a Multi-AZ RDS MySQL
database).

```
                         Internet
                            |
                      Internet Gateway
                            |
                   ┌─────── ALB (HTTP :80) ───────┐
                   │        public subnets        │
        us-east-1a │  10.0.1.0/24    10.0.2.0/24  │ us-east-1b
                   │     (+ NAT GW)               │
                   ▼                              ▼
          private 10.0.3.0/24           private 10.0.4.0/24
          ┌───────────────────┐        ┌───────────────────┐
          │ WordPress EC2      │        │ WordPress EC2      │
          │ (Auto Scaling)     │        │ (Auto Scaling)     │
          └─────────┬─────────┘        └─────────┬─────────┘
                    └──────────► RDS MySQL ◄──────┘
                         Multi-AZ, port 3306
```

## What gets created

| Component           | Resource(s)                                                  |
| ------------------- | ----------------------------------------------------------- |
| Network             | VPC, Internet Gateway, 2 public + 2 private subnets         |
| Egress              | 1 NAT Gateway (+ EIP), public & private route tables        |
| Load balancing      | Application Load Balancer, target group, HTTP :80 listener  |
| Compute             | Launch template + Auto Scaling Group (min 2 / max 4)        |
| Scaling             | Target-tracking policy at 60% average CPU                   |
| Database            | RDS MySQL 8.0, Multi-AZ, encrypted, in private subnets      |
| Secrets             | Random DB password generated by Terraform (view via output)     |
| Access / IAM        | None created; optional existing instance profile for Session Manager |
| Security groups     | `internet → ALB :80 → EC2 :80 → RDS :3306` chain            |

## Prerequisites

- [Terraform](https://developer.hashicorp.com/terraform/downloads) >= 1.5
- AWS credentials configured (`aws configure`, `AWS_PROFILE`, or env vars)
- An AWS account with permission to create the resources above

## Running in AWS Academy Learner Lab

This project is already adapted for Learner Lab:

- **No IAM is created** (the lab blocks it), so nothing to configure there.
- The DB password is generated and passed straight to the instances, so the
  project needs no SSM or IAM permissions.
- Region defaults to `us-east-1`, which the lab allows.

Things to remember in the lab:

1. **Start the lab** and wait for the dot next to "AWS" to turn green before
   running Terraform.
2. **Credentials are temporary** — copy them (with the `aws_session_token`)
   from "AWS Details → AWS CLI" into `C:\Users\<you>\.aws\credentials` each
   session. If an `apply`/`destroy` suddenly fails with a token error, your
   session expired: re-copy the credentials and run the command again.
3. **Your credit is limited.** The NAT Gateway, ALB, and Multi-AZ RDS consume
   credit the whole time they exist. Run `terraform destroy` as soon as you're
   done. End the lab session too.
4. **Session Manager (optional):** instances have no instance profile by
   default, so the site works but you can't open a shell on them. To enable it,
   find the lab's instance profile (`aws iam list-instance-profiles`, usually
   `LabInstanceProfile`) and set `instance_profile_name` in `terraform.tfvars`.

## Usage

```bash
# 1. (Optional) customise inputs
cp terraform.tfvars.example terraform.tfvars
#    edit terraform.tfvars  — or skip this; every variable has a default

# 2. Initialise providers
terraform init

# 3. Review the plan
terraform plan

# 4. Create everything (RDS Multi-AZ takes ~10–15 min)
terraform apply

# 5. Grab the site URL
terraform output wordpress_url
```

Open the `wordpress_url` in a browser. On first visit WordPress shows its
install screen; complete it to create your admin user. The database
connection is already wired up by the instance bootstrap, so you won't be
asked for DB details.

### Retrieving the DB password

```bash
terraform output -raw db_password
```

### Accessing an instance (optional)

Instances are private and have no inbound SSH. To open a shell without SSH, set
`instance_profile_name` to the lab's instance profile (see the Learner Lab
section), then:

```bash
aws ssm start-session --target <instance-id> --region us-east-1
```

## Tear down

```bash
terraform destroy
```

## File layout

```
versions.tf       provider & Terraform version constraints
variables.tf      all inputs (CIDRs, AZs, instance sizes, DB settings)
vpc.tf            VPC, IGW, subnets, NAT, route tables
security.tf       ALB / EC2 / RDS security groups
alb.tf            load balancer, target group, listener
compute.tf        AMI lookup, launch template, ASG, scaling policy
rds.tf            RDS MySQL Multi-AZ, DB subnet group, generated password
user_data.sh.tftpl  instance bootstrap: installs & configures WordPress
outputs.tf        site URL, endpoints, helpers
```

## Notes, trade-offs, and production hardening

This mirrors the diagram faithfully. A few things to know before relying on it:

- **Shared media.** Each instance keeps its own `wp-content/uploads`, so a file
  uploaded on instance A isn't visible when the ALB routes a later request to
  instance B. For a real multi-instance site, put `wp-content/uploads` (or all
  of `wp-content`) on **Amazon EFS** mounted by every instance, or offload media
  to S3 via a plugin. This is the single most important addition for production.
- **HTTP only.** The diagram specifies HTTP :80, so that's what this builds.
  For anything public-facing, add an **ACM certificate** and an HTTPS :443
  listener, and redirect :80 → :443. The bootstrap already honours the ALB's
  `X-Forwarded-Proto` header so WordPress generates correct `https://` URLs once
  you do.
- **Single NAT Gateway.** Matches the diagram and keeps costs down, but it's a
  per-AZ single point of failure for outbound traffic. For full resilience,
  create one NAT Gateway per AZ and a private route table per AZ.
- **RDS safety switches.** `skip_final_snapshot = true` and
  `deletion_protection = false` are set for easy teardown in testing. Flip both
  for production (`skip_final_snapshot = false` with a
  `final_snapshot_identifier`, `deletion_protection = true`).
- **Bootstrap at boot.** WordPress is installed via user-data on each launch.
  That's simple but slow to scale and re-downloads WordPress every time. For
  faster, more reproducible launches, bake a golden AMI (e.g. with Packer) and
  have user-data only drop in config.
- **State.** This uses local state. For teamwork, configure a remote backend
  (S3 + DynamoDB lock table) before your first apply.
- **Cost.** NAT Gateway, the ALB, and Multi-AZ RDS are the main always-on
  charges — this is **not** free-tier. Run `terraform destroy` when you're done
  experimenting.

> The specific host IPs in the diagram (10.0.3.10/.11 for EC2, 10.0.3.20/
> 10.0.4.20 for RDS) are illustrative. EC2 addresses are assigned dynamically

> pinned here — both are reached by DNS/endpoint rather than fixed IP.
